# Backend / frontend alignment audit

Audit scope: the NestJS application modules registered by `src/app.module.ts`, their controllers and DTO references, the Prisma schema, authentication guards, and the current `frontend/` App Router files. This is a source audit, not a live-server or database test. There is no global API prefix; the API listens on `PORT` (default `3000`).

## A. Existing backend modules

Registered business modules: auth, school membership, students, onboarding, teachers, classes, class levels, documents, enrollment, student lifecycle, subjects, attendance, examinations, results, fee structures, invoices, timetable, announcements, notifications, dashboard, audit logs, academic sessions, terms, parents/guardians, payments, plans, subscriptions, schools, super-admin, grading, assessment components, and scheduled jobs. Billing controllers add discounts, bulk invoicing, fee scopes, installments, receipts, and refunds. Prisma, email, and scheduled jobs are infrastructure rather than user-facing workspaces.

The schema includes six roles (`SUPER_ADMIN`, `SCHOOL_ADMIN`, `TEACHER`, `ACCOUNTANT`, `PARENT`, `STUDENT`) and records for school membership, students, guardians, teachers, academic sessions, terms, classes, subjects, enrollments, attendance, examinations/results/report cards, fees/invoices/payments/refunds/installments, plans/subscriptions, notifications, announcements, documents, audit logs, and messaging deliveries.

## C. Request and response contracts

- DTO validation is global: whitelist enabled, unknown fields rejected, and primitive transformation enabled. Request bodies are the controller's DTOs under `src/**/dto/`; query inputs are the named query DTOs. Multipart upload field names are `file`; document uploads optionally include `kind` and `name`. Student import is a CSV file and accepts `dryRun=true`.
- Auth registration accepts `{ schoolemail, password, schoolName, phone?, schooladdress? }`. The existing frontend form maps `schoolEmail`/`schoolAddress` to these backend names. Login accepts `{ email, password }` (or legacy `schoolemail`). Refresh accepts `{ refreshToken }`; reset accepts `{ token, password }`; change password accepts `{ currentPassword, newPassword }`; verification accepts `{ token }`; resend/forgot accept `{ email }`; logout accepts optional `{ refreshToken }`.
- Successful login returns `{ access_token, refresh_token, token_type: "bearer", expires_in: 900, must_change_password }`. Refresh returns the rotated `access_token`, `refresh_token`, `token_type`, and `expires_in`. These are bearer JWT + opaque refresh token; the backend does not set cookies. Registration and password/email actions return `{ message }`. `/auth/me` returns the request user `{ id, supabaseUserId, sub, email, firstName, lastName, name, displayName, role, schoolId?, mustChangePassword? }`.
- `GET /dashboard` for school admin/accountant/super admin returns `{ school: { id, name, logoUrl }, statistics: { students, teachers, parents, classes, subjects }, academic: { activeSession }, finance: { pendingInvoices, paidInvoices, revenue, failedPayments }, recentAnnouncements }`. Teacher/student/parent responses instead return school, role-specific counts, and active academic session. `/dashboard/aggregates` returns either `{ scope: "student", studentId, results, attendance }`, `{ scope: "family"|"student", students: [...] }`, or `{ scope: "school"|"class", classes: [...] }`; aggregates are computed by Prisma, not fabricated.
- `GET /super-admin/dashboard` returns nested counts: `schools { total, active, inactive, suspended }`, `users/students/teachers/parents { total }`, and `subscriptions { total, active, trial, pastDue, cancelled, expired }`.
- Pagination query inputs use `search?`, `page?` (min 1), `limit?` (1..100, default 20). Services that paginate return `{ data, meta: { page, limit, total, totalPages } }`; not every list is paginated. Many read/write endpoints return a Prisma model or selected/include shape directly, so there is no universal `{data}` response envelope. Endpoint-specific bodies and output shapes must be taken from the named controller/service/DTO before forms or tables are built.
- Finance amounts use Prisma Decimal values; frontend formatting must use school currency where returned (`School.currency`, default `NGN`) and must not invent totals. PDF endpoints return `application/pdf`; document downloads return their stored MIME type.

## D. Authentication requirements

The global JWT guard protects routes unless `@Public()` is used. Access tokens last 15 minutes; refresh tokens last seven days, are stored hashed server-side, rotate on every refresh, and token-family reuse revokes the family. Accounts must be active, school subscriptions must be in good standing for school features (except designated billing/auth routes), and a temporary password gates most routes until changed. Email verification is required unless explicitly bypassed in development. Login lockout begins after five failed attempts for 15 minutes. Logout with a refresh token revokes its family; without it terminates every active session.

The frontend BFF stores access and refresh tokens in HttpOnly cookies and returns only `must_change_password` from login. It rotates tokens through `/auth/refresh` and retries a protected request once after a 401. Logout and password change are proxied through dedicated route handlers. These flows are source-implemented but have not been tested end-to-end against a live backend.

## E. Role permissions and school access

- Backend roles are exactly the six enum values listed above. Backend role guards and service checks, not frontend navigation, authorize actions.
- Super admin has platform counts, all-school listing/status, subscription/plan administration, and access to school-level data only where services explicitly permit it. The current backend provides no paginated school-admin CRUD console or arbitrary tenant-switch endpoint.
- School admin owns school setup, school users/memberships/invitations, academic configuration, student lifecycle, staff/guardian records, attendance, assessments/results/report cards, communications, fees/invoices, subscriptions, and school settings, subject to each endpoint's service rules.
- Teacher reads assigned classes/rosters/students and handles supported attendance/results/report-card remarks; services restrict class/student access to assignments. Teacher attendance/history routes are explicit. No payroll or staff HR endpoint exists.
- Accountant can access dashboard, fee structures, invoices/payments, fee scopes, discounts, bulk invoicing, installments, refunds, receipts, class levels, subjects, announcements, and own notifications only where the service permits. It cannot be assumed to have school settings, student CRUD, or admin mutation rights.
- Parent access is linked-child scoped: parent profile, child details/timetable/attendance, own results/report cards/invoices/payments and readable announcements/notifications where implemented. Never accept arbitrary student identifiers as proof of access.
- Student access is self-scoped: `students/me`, own attendance/results/report cards/invoices/payments, timetable, announcements/notifications, and own document/history routes where service permits.
- `SchoolAccessGuard` only enforces that a user has a membership when explicitly applied. Other services perform their own membership/tenant checks. JWT role resolution uses the first membership loaded by `createdAt`; this is not a tenant picker. A school admin feature must not send arbitrary `schoolId` unless its backend contract explicitly accepts it.

## F. Tenant and billing behavior

School memberships connect users to schools and carry a role. Most school resources include `schoolId` and rely on the service to resolve the current membership and constrain reads/writes. The JWT guard blocks inactive schools and, unless enforcement is bypassed in configured development, blocks school features without a current active/trial subscription; subscription management, active plans, auth, and payment verification are exceptions. The school ID in UI state is contextual only and must never weaken backend checks.

## J. Frontend alignment and implementation status

The frontend is Next.js 15 App Router + React 19 + TypeScript. It now has a Schoolhouse marketing site, backend-driven pricing, role-aware authenticated AppShells, a shared typed API client, and a server-side backend proxy. Marketing claims describe only capabilities present in the backend. Dashboard counts and workspace records are fetched from the API; pages render loading, error, and empty states instead of sample records or fabricated metrics. `/super-admin` redirects to the live `/dashboard` rather than maintaining a second placeholder.

The BFF stores access and refresh tokens in HttpOnly cookies and removes both tokens from the browser-visible login response. It refreshes and retries a request once after a 401, and exposes logout and password-change handlers. Registration field mapping matches the backend DTO. Login, email verification, password recovery/reset, forced password change, and invitation acceptance screens are present. Role navigation is a usability aid only; backend guards remain authoritative. The notifications workspace can mark the current user's own notification as read using the backend endpoint.

Most workspace screens are currently read-only. School administrators can create a student profile using the backend DTO; that action does not claim to enroll the student in a class. Users can mark their own notifications as read. The frontend does not yet implement the broader update/billing workflows listed in Sections B and G-I; do not imply that a visible list page is a complete management workflow. Before adding a mutation, inspect the endpoint's DTO, controller permissions, and service scoping. In particular, do not accept client-supplied tenant/student identifiers as authorization. API behavior and role access have not been verified against a running backend and database.

For local development, the frontend listens on port `3001` while the backend defaults to `3000`; set `frontend/.env`'s `API_BASE_URL` to the backend origin. Configure the backend's `FRONTEND_URL` (and `APP_URL` where invitation links use it) to `http://localhost:3001`, and allow that origin in `CORS_ORIGINS`, so verification and invitation links return to the frontend.

## Implementation status

This document records the source audit and is the boundary for the redesign. Any endpoint-specific form must use its source DTO; any dashboard visualization must use the endpoint response; missing capabilities stay documented rather than mocked. A production-ready experience still requires API- and role-specific tests against a configured backend, which is not available in this repository session.
